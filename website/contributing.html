Contributing Guide

Thank you for your interest in contributing to LLM-TUI! This guide will help you get started with contributing to the project.

Code of Conduct

Please note that this project adheres to a code of conduct. By participating, you are expected to uphold this code. Be respectful, inclusive, and constructive in all interactions.

How to Contribute

Reporting Bugs

Before creating bug reports, please check the existing issues to avoid duplicates. When creating a bug report, include:

  • Clear and descriptive title
  • Steps to reproduce the issue
  • Expected behavior vs actual behavior
  • System information (OS, Rust version, etc.)
  • Logs (set RUST_LOG=debug for detailed logs)
  • Screenshots if applicable

Suggesting Features

Feature suggestions are welcome! When suggesting a feature:

  • Use a clear and descriptive title
  • Provide a detailed description of the feature
  • Explain why this feature would be useful
  • Include examples or mockups if possible
  • Check if similar features already exist

Pull Requests

We love pull requests! Here's the process:

  1. Fork the repository
  2. Create a feature branch (git checkout -b feature/amazing-feature)
  3. Make your changes
  4. Follow the coding standards (see below)
  5. Write or update tests as needed
  6. Ensure all tests pass
  7. Commit your changes (git commit -m 'Add amazing feature')
  8. Push to the branch (git push origin feature/amazing-feature)
  9. Open a Pull Request

Development Setup

Prerequisites

  • Rust 2024 edition or later
  • Git
  • SQLite development libraries
  • A code editor (VS Code, Vim, etc.)

Setting Up the Development Environment

# Clone your fork
git clone https://github.com/YOUR_USERNAME/llm-tui.git
cd llm-tui

# Add upstream remote
git remote add upstream https://github.com/klt-mm/llm-tui.git

# Install development dependencies
cargo install cargo-watch cargo-nextest

# Build the project
cargo build

# Run tests
cargo test

# Run the application
cargo run

Development Workflow

We recommend using cargo-watch for automatic rebuilding:

# Watch for changes and rebuild
cargo watch -x check

# Watch and run tests
cargo watch -x test

# Watch, check, and run tests
cargo watch -s "cargo check && cargo test"

Coding Standards

Rust Style Guide

  • Follow the official Rust Style Guide
  • Use cargo fmt to format code before committing
  • Ensure cargo clippy passes with no warnings
  • Write clear, descriptive variable and function names
  • Add comments for complex logic, but prefer self-documenting code

Code Organization

The project follows a layered architecture:

TUI (ratatui)
  ↓
Application / Services (app.rs, events.rs)
  ↓
Domain (src/domain/)          ← must not import ratatui, sqlx, reqwest, or terminal APIs
  ├── LLM Provider (src/llm/)
  └── Repositories (src/persistence/)
        ↓
      SQLite + FTS5

Important: The domain layer must never depend on infrastructure crates (ratatui, sqlx, reqwest, terminal APIs).

Testing

All code changes must include appropriate tests:

  • Unit tests: For pure functions and domain logic
  • Integration tests: For repository operations and app flows
  • TUI tests: For UI rendering (when applicable)

Run tests with:

# Run all tests
cargo test

# Run specific test file
cargo test --test phase6

# Run with output
cargo test -- --nocapture

Commit Messages

Write clear, descriptive commit messages:

  • Use the imperative mood ("Add feature" not "Added feature")
  • Start with a capital letter
  • Keep the first line under 72 characters
  • Include a detailed description if needed
  • Reference issues when applicable

Example:

Add tool calling support for OpenAI providers

- Implement ToolDefinition, ToolCall, and ToolResult domain types
- Add ToolExecutor trait and ToolRegistry
- Implement built-in tools: shell, read_file, write_file, list_directory
- Add tool orchestration in app.rs
- Add UI rendering for tool calls and results
- Add comprehensive tests in tests/phase6.rs

Closes #42

Quality Gates

All pull requests must pass the following quality gates:

# Format check
cargo fmt --all -- --check

# Clippy lint check
cargo clippy --all-targets --all-features -- -D warnings

# All tests
cargo test --all-features

# Build release
cargo build --release

These checks are also run automatically by CI on every pull request.

Documentation

When adding new features, update the relevant documentation:

  • Update README.md if adding user-facing features
  • Update design docs in docs/ for architectural changes
  • Add inline documentation for public APIs
  • Update the website documentation if needed

Architecture Decisions

When making significant architectural decisions:

  • Discuss in an issue first before implementing
  • Consider backwards compatibility
  • Document the rationale in the PR description
  • Update design docs if the architecture changes

Getting Help

If you need help with your contribution:

  • Check existing issues and discussions
  • Ask questions in the issue you're working on
  • Reach out to maintainers

Recognition

All contributors are recognized in the project. Your contributions help make LLM-TUI better for everyone!
